# Надёжная доставка (transactional outbox)

Цель: **ответ гостя и уведомление владельцу не теряются** при ошибках, обрывах интернета, сбоях Telegram API,
перезапуске сервера и закрытии приложения; одно и то же не доставляется дважды.

## Как это работает

```
Mini App                         Backend                              Telegram
────────                         ───────                              ────────
[Отправить]
 1. сохранить на устройстве
    (localStorage, clientId)
 2. POST /api/rsvp ───────────►  BEGIN
                                  INSERT rsvp_responses (client_id UNIQUE)
                                  INSERT outbox (dedupe_key UNIQUE)   ← одна транзакция:
                                 COMMIT                                  либо оба, либо ничего
    ◄── 201 {success} ───────────
 3. удалить с устройства
    ТОЛЬКО после 201/200
                                 worker (каждые 5 с + сразу после записи)
                                  claim (compare-and-set) ──────────► sendMessage
                                  sent / retry с паузой / failed  ◄── ok | ошибка
```

Если на шагах 2–3 что-то не удалось (нет сети, 5xx, таймаут, ответ потерян), приложение **само повторяет** с тем же
`clientId`: при появлении связи (`online`), при возврате в приложение, при следующем открытии и по таймеру
(2 с → 4 с → … → 60 с). Сервер по `clientId` понимает, что это повтор, и **не создаёт** вторую запись и второе
сообщение (ответ `200 {duplicate:true}`).

## Состояния `outbox`

| Статус | Значение |
|---|---|
| `pending` | ждёт отправки (новое, либо ждёт времени следующей попытки) |
| `sending` | worker отправляет прямо сейчас. Если процесс упал — через `OUTBOX_STALE_MS` (90 с) задание вернётся в работу |
| `sent` | доставлено (`sent_at`) |
| `failed` | постоянная ошибка (бот заблокирован, чат не найден) или закончились попытки. **Не удаляется**, ждёт `/retry` |

Классификация ошибок Telegram:

| Ошибка | Действие |
|---|---|
| сеть, таймаут, 5xx, 401 (токен меняют) | `pending`, повтор: 5 с, 10 с, 20 с … до 1 ч (+jitter), до 30 попыток |
| 429 Too Many Requests | `pending`, пауза = `retry_after` из ответа Telegram |
| 400 / 403 / 404 (бот заблокирован, чат не найден) | `failed` сразу, причина в `last_error` |

## Гарантии и честные ограничения

* **Не теряется:** запись и задание создаются атомарно; задание живёт в БД, а не в памяти процесса; ничего не удаляется
  при неудачных попытках (`sent` чистятся через 90 дней, `failed` — никогда).
* **Доставка — at-least-once.** Единственный случай, когда сообщение может прийти дважды: Telegram **принял**
  сообщение, но связь оборвалась **до** ответа боту (или процесс упал между ответом Telegram и пометкой `sent`).
  Точно-однократная доставка в Telegram API принципиально невозможна. Поэтому в каждом сообщении есть номер `№N`:
  повтор сразу узнаётся. Окно крайне узкое (миллисекунды).
* Всё, что относится к приложению↔серверу, дедуплицируется **строго** (`client_id` + уникальный индекс).
* Если сервер недоступен дольше, чем живёт приложение, данные ждут на устройстве (localStorage) и уходят при следующем открытии.
  Если WebView очистил хранилище до этого, ответ потерян. Это ограничение платформы.
* Если база недоступна при старте, сервер повторяет миграцию, а не падает.

## Контроль

* Бот (только `ADMIN_CHAT_ID`): `/status` (счётчики, возраст самого старого недоставленного, последние ошибки) и
  `/retry` (вернуть `failed` в очередь).
* API: `POST /api/admin/outbox` и `POST /api/admin/outbox/retry` (тело `{tgInitData}`, только администратор).
* Логи: `[outbox] #id qayta uriniladi …` (повтор) и `[outbox] #id FAILED …` (постоянная ошибка).

## Настройки (необязательные переменные окружения)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OUTBOX_INTERVAL_MS` | 5000 | как часто worker проверяет очередь |
| `OUTBOX_BATCH` / `OUTBOX_CONCURRENCY` | 10 / 5 | размер партии / одновременных отправок |
| `OUTBOX_STALE_MS` | 90000 | когда `sending` считается «зависшим» |
| `OUTBOX_MAX_ATTEMPTS` | 30 | предел попыток для временных ошибок |
| `OUTBOX_BACKOFF_BASE_MS` / `_CAP_MS` | 5000 / 3600000 | пауза между попытками: база и потолок |
| `OUTBOX_SEND_TIMEOUT_MS` | 20000 | оборвать зависший вызов Telegram |
| `OUTBOX_KEEP_SENT_DAYS` | 90 | через сколько дней чистить `sent` |

## Как добавить новое уведомление (напоминания, сообщения, статистика…)

Любая будущая отправка в Telegram идёт **только** через outbox:

```js
const outbox = require('./outbox');
// внутри транзакции вместе с бизнес-данными (db — client) или отдельно (db — pool):
await outbox.enqueue(client, {
  type: 'reminder',            // для статистики/фильтров
  chatId,                      // кому
  text: '…',                   // готовый текст (HTML)
  dedupeKey: `reminder:${weddingId}:2026-11-14`,  // тот же ключ второй раз не запишется → без дублей
});
outbox.kick();                 // после COMMIT: доставить сразу
```

Для периодических напоминаний достаточно планировщика, который раз в N минут вызывает `enqueue` с детерминированным
`dedupeKey` — повторный запуск планировщика не создаст дублей.

## Масштабирование

* Захват задания — `UPDATE … WHERE id=$1 AND (status='pending' …) RETURNING *` (compare-and-set): несколько
  экземпляров сервера могут работать одновременно, каждое задание возьмёт ровно один.
* Узкое место — лимиты Telegram (~30 сообщений/с всего, ~1/с в один чат; 429 обрабатывается автоматически),
  а не БД. Нагрузочный тест: 100 параллельных RSVP принято и доставлено за ~0,4 с без дублей.
* Рост таблицы ограничен очисткой `sent`; индекс `(status, next_attempt_at)` держит выборку быстрой.
* Следующий шаг при очень большой нагрузке: `FOR UPDATE SKIP LOCKED` или отдельный worker-процесс (код
  worker'а уже не зависит от HTTP-сервера).
